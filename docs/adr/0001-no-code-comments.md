# 0001. コードコメントを書かない

- 状態: 採用
- 記録日: 2026-11-21

## 背景

コメントはコードと一緒に更新されないため、すぐに古くなる。実際、削除前に棚卸しした 858 行のコメントのうち、大半は次のどれかだった。

- **Tautology**: コードを読めば分かることの言い直し（`# Skip if IME is composing`）
- **Stale**: すでに変わった実装を説明している（例: カーソルをインデックスで保持していた頃の説明がテストに残っていた）
- **Excuse**: 手抜きの実装を正当化している（「その他のネットワークエラーは候補なし扱い」）。コーディングエージェントはこうしたコメントを前例として読み、同じ手抜きを他の場所にも広げる

本当に価値があるのは、コードからは読み取れない **Decision Record**（なぜそうしたか）だけで、それはコードの横ではなく ADR に置くほうが探しやすく、レビューもしやすい。

## 決定

- 新しいコメントは書かない。意図は命名・メソッド抽出・テストで表現する
- コードから読み取れない判断は `docs/adr/` に ADR として書く
- 手抜きを説明したくなったら、コメントを書かずに直すか、イシューを立てる
- `bin/lint-comments` が `bin/ci` の中で次の 2 点を検査する
  - ファイルのコメント数がベースライン（`config/comment_ratchet.yml`）より増えたら失敗する
  - 減ったのにベースラインを更新していない場合も失敗する。`bin/lint-comments --update` で下げ、ベースラインは下げる方向にしか動かない
- 例外: shebang、マジックコメント（`frozen_string_literal` / `rubocop:disable` 等）、ERB の strict locals（`<%# locals: ... %>`）
- 対象外: `bin/`（binstub）、`db/*schema.rb`（自動生成）、`.kamal/hooks/*.sample`、`vendor/`

## 結果

- Rails / Kamal のジェネレータが出力した設定ファイル（`config/environments/*.rb`、`config/puma.rb`、`config/deploy.yml`、`Dockerfile` など）のコメントは、初回の PR ではベースラインに残している。`rails app:update` で差分を取り込むときにノイズになるため、扱いは別途判断する
- 同じ作業を繰り返すときは `/delete-comment` スキルを使う
